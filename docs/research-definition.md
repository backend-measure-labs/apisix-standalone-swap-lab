# 연구 정의

> 측정 전에 고정한 정의입니다. 측정 뒤 바꾼 것은 「변경 기록」 절에 사유와 함께 남깁니다.

## 1. 목적

### 막으려는 손실 (EX1)

**앱 컨테이너를 새 이미지로 바꾸는 동안, 이미 시작된 다운로드가 끝까지 받아지지 않고 끊긴다.**

| 항목 | 내용 |
|---|---|
| 누가 | 대용량 파일을 내려받는 사용자 |
| 무엇을 잃는가 | 진행 중이던 다운로드. 다운로드는 이어받기가 없어 처음부터 다시 받아야 합니다 |
| 서비스 성격 | 요청 수는 적고 전송 하나가 길고 큽니다. 그래서 요청률 · 처리량은 판단에 쓰이지 않습니다 |
| 범위 밖 손실 | 업로드는 청크 단위로 재개되어 끊겨도 이어집니다 |

### 질문 (EX2)

| 구분 | 질문 |
|---|---|
| 주질문 | 기준 운영 환경에서 앱 컨테이너를 교체할 때, 진행 중 다운로드를 끊지 않는 방식이 있습니까? |
| 부질문 | 그 방식은 교체 중에 새로 시작하는 다운로드도 실패시키지 않습니까? |

답은 비교군마다 「끊긴다 · 안 끊긴다 · 조건부(종료 방식에 따라 다름)」 셋 중 하나입니다.

## 2. 조건

### 2.1 기준 운영 환경

| 항목 | 값 |
|---|---|
| 호스트 | x86_64 Ubuntu 24.04 |
| Docker / Compose | 29.2.0 / v5.0.2 |
| 앞단 | APISIX 3.15.0 standalone (`role: data_plane`, `config_provider: yaml`) |
| 설정 마운트 | `apisix.yaml` 단일 파일 바인드 마운트 |
| 업스트림 | `upstreams` 객체를 `upstream_id` 로 참조, 노드는 `서비스명:포트` (compose 내장 DNS), 타임아웃 connect 3초 · read 300초 · send 300초 |
| DNS 캐시 | `dns_resolver_valid` 미지정 (레코드 TTL 을 따름) |
| 다운로드 최장 길이 | 미확인. 이 값과 `stop_grace_period` 의 대소가 결론을 바꾸므로 두 경우를 다 잽니다 (2.3 공통 요인) |
| 서비스당 컨테이너 | 1개 |
| 현재 배포 | `docker compose up -d --no-deps <svc>` (재생성) |

| E4 | `retries` 를 정하지 않으면 노드 수 - 1 이라, 노드가 1개면 재시도가 없습니다 | [balancer.lua](https://github.com/apache/apisix/blob/3.15.0/apisix/balancer.lua) |
| E5 | `docker stop` 은 SIGTERM 을 보내고 StopTimeout(compose `stop_grace_period`, 기본 10초) 뒤 SIGKILL 합니다 | [docker stop](https://docs.docker.com/reference/cli/docker/container/stop/) · [compose services](https://docs.docker.com/reference/compose-file/services/) |

### 2.3 비교군 (EX4)

| 비교군 | 무엇을 하는가 | 판정 | 넣거나 제외한 근거 | 출처 |
|---|---|---|---|---|
| C0 재생성 | 옛 컨테이너를 멈추고 지운 뒤 새 컨테이너를 만듭니다 | 채택 (대조군) | 지금 운영 방식입니다 | [compose up](https://docs.docker.com/reference/cli/docker/compose/up/) |
| C1 scale 롤링 | 서비스를 2개로 늘려 새 컨테이너가 healthy 가 되면 옛것을 `docker stop` · `rm` 합니다. 업스트림은 서비스명 그대로입니다 | 채택 | 단일 호스트 compose 무중단에 널리 쓰는 도구입니다. 자작 스크립트 편향을 피합니다. 버전 v0.14 고정 | [wowu/docker-rollout](https://github.com/wowu/docker-rollout) |
| C2 blue/green + yaml 노드 교체 + drain | 쉬는 색 서비스를 띄워 healthy 뒤 `apisix.yaml` 노드를 같은 파일에 덮어써 바꾸고, 반영을 확인한 뒤 옛 색의 진행 중 다운로드가 0 이 될 때까지 기다렸다가(최대 600초) `docker compose stop` · `rm` 합니다 | 채택 (추천안) | APISIX standalone 의 공식 갱신 경로(E1)만 쓰는 전환입니다. 새 요청이 한 번에 옮겨지므로 옛 색을 마감 없이 비울 수 있는 유일한 후보입니다 | E1 |
| traffic-split 가중치 | 라우트 안에서 업스트림 가중치를 바꿉니다 | 제외 | 완전 전환만 보면 C2 와 같은 yaml 갱신이고, 인라인 업스트림은 헬스체크 · 재시도가 없습니다 | [traffic-split.md](https://github.com/apache/apisix/blob/3.15.0/docs/en/latest/plugins/traffic-split.md) |
| 두 노드 상시 등재 + 헬스체크 | 노드 두 개를 늘 두고 헬스체커가 빼고 넣습니다 | 제외 | 새 요청의 실패를 줄이는 장치이고, 진행 중 다운로드의 끊김은 옛 프로세스 종료가 정합니다. 종료는 C0 · C1 · C2 공통 요인으로 따로 봅니다 | [health-check](https://github.com/apache/apisix/blob/3.15.0/docs/en/latest/tutorials/health-check.md) |
| DNS 캐시 단축 · 별칭 이동 · DNS 디스커버리 | C1 의 새 요청 전환을 빠르게 합니다 | 제외 | 전환 메커니즘이 C1 과 같은 DNS 해석입니다. 진행 중 다운로드에는 영향이 없습니다 | E2 · E3 |
| 앞단 교체 (Traefik 등) | 다른 프록시로 바꿉니다 | 제외 | 앞단이 APISIX 라는 전제를 깹니다 | - |

**공통 요인: 옛 프로세스 종료 방식 3수준.** C0 · C1 에서 진행 중 다운로드가 끊기는 시점은 옛 프로세스가 연결을 닫는 시점이고, 그 시점은 종료 방식과 `stop_grace_period` 대비 다운로드 길이가 정합니다(E5 · E6). 운영 다운로드 최장 길이가 미확인이라 유예가 다운로드보다 짧은 경우와 긴 경우를 다 겁니다.

| 수준 | 앱 동작 | `stop_grace_period` | 다운로드(20초)와 비교 |
|---|---|---|---|
| L1 | SIGTERM 을 받으면 바로 종료 | 10s (기본값) | - |
| L2 | SIGTERM 을 받으면 새 연결을 받지 않고 진행 중 응답을 8초까지 기다린 뒤 종료 | 10s (기본값) | 유예가 짧음 |
| L3 | 같은 동작, 55초까지 기다림 | 60s | 유예가 김 |

## 3. 절차

### 3.1 평가 기법 (EX5)

실패는 엔진 동작이 정하는 구간(옛 프로세스 종료 · DNS 캐시 · 설정 반영 전)에서 납니다. 그래서 원전 분석으로 구간을 예측하고, 이벤트 타임라인 실측으로 그 구간이 있는지 확인합니다. 회차는 비교군 × 종료 수준마다 5회입니다. 반복은 타이머 위상(E1 의 1초 주기) 차이를 덮기 위한 것이고 확률을 추정하지 않습니다.

### 3.2 사전 관측

가설의 미확인 전제를 측정 전에 닫습니다. 결과로 가설을 바꾸면 측정 전에 「변경 기록」에 남깁니다.

| 번호 | 관측 | 걸리는 비교군 | 방법 |
|---|---|---|---|
| P1 | 내장 DNS 가 주는 TTL (moby 소스는 600초) | C1 | 컨테이너 안에서 `dig app` |
| P2 | scale 2 일 때 서비스명이 주소 2개를 돌려주는가 | C1 | `dig app` |
| P3 | 새 컨테이너가 healthy 전에 DNS 에 나오는가 | C1 | 기동 지연 5초 앱으로 0.2초마다 `dig` |
| P4 | 같은 초 안의 두 번 쓰기가 둘 다 반영되는가 | C2 롤백 | 0.3초 간격 두 번 쓰기 × 10회 |
| P5 | 제자리 쓰기와 교체 쓰기(rename)가 반영되는가 | C2 | 방식별 5회 |
| P6 | 노드를 바꾼 뒤 옛 노드로 가던 진행 중 다운로드가 끝까지 받아지는가 | C2 | 옛 컨테이너를 멈추지 않고 노드만 바꿈 × 5회 |

### 3.3 가설과 반증 조건 (EX3)

| 비교군 × 종료 | 예측 | 근거 | 반증 조건 |
|---|---|---|---|
| C0 × L1 | 진행 중 다운로드가 매 회차 끊김. 새 다운로드는 옛것 정지 \~ 새것 수신 가능 사이에 시작 실패 | E5, 노드 1개 · 재시도 없음(E4) | 끊김 0 인 회차 |
| C0 × L2 | 유예(10초)를 넘는 진행 중 다운로드가 끊김. 새 다운로드는 SIGTERM \~ 새것 수신 가능 사이에 시작 실패 | E5 | 끊김 0 인 회차 |
| C0 × L3 | 진행 중 다운로드는 안 끊김. 새 다운로드는 SIGTERM \~ 새것 수신 가능 사이(진행 중 다운로드가 끝날 때까지 포함)에 시작 실패 | E5 | 끊김 > 0, 또는 시작 실패 0 |
| C1 × L1 | 옛것 정지 때 진행 중 다운로드 끊김. 새 다운로드는 옛것 정지 뒤 DNS 캐시가 옛 주소를 쥔 동안(TTL, P1) 시작 실패 | E2 · E3 · E5 | 끊김 0 인 회차 |
| C1 × L2 | 유예를 넘는 진행 중 다운로드가 끊김. 새 다운로드는 C1 × L1 과 같이 시작 실패 | E2 · E3 · E5 | 끊김 0 인 회차 |
| C1 × L3 | 진행 중 다운로드는 안 끊김. 새 다운로드는 C1 × L1 과 같이 시작 실패 | E2 · E3 · E5 | 끊김 > 0, 또는 시작 실패 0 |
| C2 × L1 · L2 · L3 | 진행 중 끊김 0, 시작 실패 0. drain 이 옛 색의 진행 중 다운로드를 다 보낸 뒤 멈추므로 종료 방식과 상관없습니다 | E1 · E6 | 어느 회차든 끊김 또는 시작 실패 > 0 |

C1 의 시작 실패 구간 끝은 DNS 캐시 만료(TTL)라 측정 창(배포 뒤 30초)보다 깁니다. 구간 끝은 P1 의 TTL 로 정하고, 실측은 구간의 시작과 측정 창 끝까지 이어지는지만 봅니다.

### 3.4 시나리오와 회차

| 항목 | 값 |
|---|---|
| 다운로드 | 20MB 를 1MB/s 로 보냅니다 (한 건 약 20초). 대용량 전송을 짧게 재현한 값입니다 |
| 다운로드 시작 | 측정 창 동안 1초마다 1건 시작 (교체 순간에 진행 중 다운로드가 약 20건 걸립니다) |
| 측정 창 | 다운로드 시작 30초 → 배포 1회 → 배포 끝난 뒤 30초 더 시작 → 모든 다운로드 종료 대기 |
| 회차 | 비교군 3 × 종료 3 × 5회 = 45회 |
| 순서 | 비교군 · 종료 수준 조합을 무작위로 섞습니다 |

### 3.5 지표 (EX6)

| 지표 | 정의 | 손실과의 관계 |
|---|---|---|
| 끊긴 다운로드 수 | HTTP 200 으로 받기 시작했지만 받은 바이트 < 20MB 이거나 curl 종료 코드 ≠ 0 인 것 | 손실을 직접 셉니다. 시작 시각과 관계없이 받은 바이트로 가릅니다 |
| 시작 실패 수 | HTTP 200 을 받지 못한 것 (연결 오류 · 5xx) | 부질문 |
| 이벤트 타임라인 | 새것 기동 · healthy · yaml 쓰기 · 반영 확인 · drain 끝 · 옛것 SIGTERM · 옛것 제거 시각, docker 컨테이너 이벤트 | 끊김 · 시작 실패가 어느 구간에서 났는지 나눕니다. 시작 시각은 이 귀속에만 씁니다 |
| 다운로드별 서버 | 응답 헤더 `X-Version` · `X-Host` | 어느 컨테이너가 보냈는지 |

다운로드는 기존 도구인 curl 로 받고 `-w` 로 받은 바이트 · 종료 코드 · HTTP 코드를 남깁니다. 모든 시각은 같은 호스트 시계(`date +%s.%N`)로 찍습니다.

### 3.7 통제 변수와 편향 방지 (EX8)

| 항목 | 내용 |
|---|---|
| 같은 시험 | 모든 조합이 같은 다운로드 패턴 · 회차 · 앱 이미지 · healthcheck 를 받습니다 |

| 회차 제외 | 하네스 오류(리셋 실패 · 이미지 빌드 실패)만 제외하고, 제외 회차의 원시 기록도 남깁니다 |

## 4. 결론의 크기 (EX9)

- 결론은 「이 환경에서 5회 실측해 구간이 있었다 · 없었다」 크기로만 씁니다. 0/5 는 「끊김이 없다」가 아니라 「5회에서 나오지 않았다」입니다.
- 무중단 판정의 근거는 실측 횟수가 아니라 엔진 동작(E1 · E5 · E6)과 실측 타임라인이 맞는가입니다.
- 성공 · 실패 · 미수행을 모두 적습니다.
